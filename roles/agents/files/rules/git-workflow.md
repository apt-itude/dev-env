# Git & PRs

- ALWAYS use git worktrees for code changes - never work directly in the main checkout
  - fetch latest from origin and branch from `origin/{base-branch}`
- never push directly to the base branch (main/master) - always create a branch and PR for changes
- when creating a git branch name use at/{ticket}/{some-detail}
  - if there is no ticket just do at/{some-detail}
  - don't attempt to use the GitHub user or Linear user as the branch prefix
- always use conventional commits: https://www.conventionalcommits.org/en/v1.0.0/
- pull request titles should also follow the conventional commits style
- when creating github pull requests always do so in draft mode
  - this applies at CREATION time only. Never move an existing PR back to draft.
  - the draft/ready state is mine to control once the PR exists. If a PR is already
    marked ready-for-review when you go to update it, leave it ready — push your
    commits and do nothing to its draft state. Never run `gh pr ready --undo` (or
    otherwise re-draft a PR) to "restore" draft mode, even if you think something
    else marked it ready. If a PR's ready state ever seems wrong, ask me rather than
    changing it.
- when creating pull requests always assign them to me
- PR descriptions should be extremely concise so that a human reviewer can quickly understand what they are reviewing: include only a few sentences about **why** the change is being made and a bulleted list summarizing **what** is changing and how each change addresses the problem.
  - the "what" section should also be extremely concise and tailored to human readers. It should describe the nature of the changes in plain language rather than referencing filenames, line numbers, code snippets, etc. The reviewer will look at the code diff in the PR to understand the technical details of change, so this section should serve as a useful summary that augments the diff rather than duplicate information.
- when including validations in the pr description keep it simple - often most stuff is automated via actions/etc so just include things I would need to manually do
- for architectural changes or new architecture, generate simple Mermaid diagrams in the PR description to illustrate the change visually
- before creating PRs, always check if tests pass locally first
- before pushing to an existing pull request, always check the state of the PR first to ensure it hasn't been closed already. If it has, ask me whether I want to create a new pull request with the follow-up change.
- whenever you post a PR description or a GitHub comment (PR or issue), append a small footer on its own line at the end indicating which AI agent generated it. Use exactly the following, replacing `<agent>` with your product name (e.g. Claude, Codex, OpenCode):

  ```
  ---
  _🤖 Generated by <agent>_
  ```

  Add the footer once, only to content you author; never strip or duplicate a footer that's already present.
  - skip this footer for any content where your harness already instructs you to append its own attribution line (e.g. Claude Code's "🤖 Generated with Claude Code" on PR descriptions) — use the harness's line alone so there's only one attribution. Still add this footer to content the harness doesn't attribute (e.g. GitHub comments).
